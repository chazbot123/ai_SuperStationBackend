# 生成工作台布局与提示词润色设计

## 背景

当前 `社媒图文生成` 与 `商品图与详情图生成` 页面已具备基础生成功能，但页面主次关系仍偏向“左侧输入”，与目标参考图中的“右侧结果为主、左侧配置为辅”的工作台形态不一致。同时，用户已输入提示词后仍需要手工整理描述，缺少“一键润色”能力。

本次设计目标是在不改动现有生成业务主链路的前提下，将两个页面统一为更接近参考图的双栏工作台，并为提示词输入区补充文字大模型润色能力。

## 目标

- 将两个页面统一为“左侧配置、右侧结果”的生成工作台。
- 左侧固定为四段结构：当前模型显示、上传参考图、提示词输入框、参数。
- 右侧结果区在桌面端明显放大，成为主视觉区域。
- 页面标题区、说明文案、按钮排布、空态面板、边框层级尽量贴近参考图。
- 为两个页面提供“提示词润色”功能，基于当前已输入内容调用文字模型生成更适合下游生成任务的提示词，并直接回填。
- 保持现有社媒图文生成、商品图生成、草稿保存与结果编辑能力不变。

## 非目标

- 不改动视频生成页面。
- 不新增独立的“提示词模型配置”类型，先复用现有文字模型配置。
- 不重做全站通用布局，只聚焦这两个页面。
- 不重构当前 AI 结果存储结构。

## 方案对比

### 方案 A：完整复刻式工作台

直接调整两个页面结构与样式，使其尽量对齐参考图的左右比例、标题区、卡片层级与结果空态，并接入提示词润色接口。

优点：
- 最接近目标效果。
- 两个页面视觉统一。
- 对用户感知最明显。

缺点：
- 页面结构改动较大。

### 方案 B：仅扩大结果区

保留现有结构，只调列宽并增加润色按钮。

优点：
- 改动最小。

缺点：
- 很难达到“几乎一模一样”的观感。

### 方案 C：先抽通用工作台组件再接页面

先抽象共享工作台，再改两个页面。

优点：
- 后续可复用性更好。

缺点：
- 本次实现成本最高，超出当前需求最小闭环。

推荐采用方案 A。

## 页面设计

## 共同布局

- 页面主体采用双栏桌面布局，左窄右宽。
- 左栏承载配置输入，右栏承载当前生成结果。
- 左栏宽度保持稳定，右栏尽量拉大，可采用接近 `0.9fr / 1.1fr` 或更偏向右侧的比例。
- 两栏外层使用统一深色容器，顶部含标题、说明与右上角动作按钮。
- 结果区最小高度提升，空态时仍保持大面板视觉。

## 左栏结构

左栏顺序固定如下：

1. 当前模型显示
2. 上传参考图
3. 提示词输入框
4. 参数

### 当前模型显示

- 显示当前启用的文字模型与图片模型。
- 采用更接近参考图的紧凑模型卡样式，突出模型名称与启用状态。
- 社媒图文页展示“文字模型 + 图片模型”。
- 商品图页同样展示“文字模型 + 图片模型”。

### 上传参考图

- 参考图区域单独成组，包含预览区域、上传按钮、清空按钮。
- 继续支持拖拽上传。
- 文档素材如仍需保留，则视觉上降级为补充说明，不抢占参考图区主视觉；参考图区主展示对象为图片。

### 提示词输入框

- 输入框高度提升，右上或标题行放置“润色”按钮。
- “润色”仅基于当前用户已输入文本工作，不自动拼接额外提示后再回填给用户。
- 润色后直接覆盖输入框内容，并给出轻量成功提示。
- 若输入为空则不调用接口，直接提示先输入内容。
- 润色中按钮显示加载态，防止重复触发。

### 参数

- 参数项整理为更紧凑的双列或分组样式。
- 社媒图文页保留平台风格、尺寸、分辨率。
- 商品图页保留商品名称、卖点、目标人群、尺寸、分辨率，其中商品信息类字段仍位于左栏配置区，但视觉上归入参数组。

## 右栏结果区

- 标题固定为“当前生成结果”。
- 顶部保留刷新按钮。
- 空态大面板样式尽量对齐参考图：深底、细边框、居中说明。
- 有结果时，编辑区更宽更高，标题、正文、标签、图片编辑均在同一主面板内展开。
- 图片网格在右侧显示时可适当放大缩略图比例。

## 页面差异

### 社媒图文生成页

- 左栏参数强调平台风格与图文规格。
- 右栏结果保留标题、正文、标签、图片编辑。

### 商品图与详情图生成页

- 左栏参数中保留商品名称、核心卖点、目标人群。
- 右栏结果保留标题、详情文案、图片编辑。

## 提示词润色能力

## 前端交互

- 两个页面在提示词区域新增 `润色` 按钮。
- 点击后读取当前 `userPrompt`。
- 成功后将返回文本直接写回 `userPrompt`。
- 失败时显示后端错误信息或统一失败提示。

## 后端接口

- 在 `server/src/modules/ai` 下新增提示词润色 DTO 与接口。
- 新接口形式：`POST /api/ai/prompt-polish`。
- 输入：
  - `prompt`: 用户当前提示词
  - `scene`: `social_post` 或 `product_image`
  - `modelConfig`: 当前启用文字模型配置
- 输出：
  - `prompt`: 润色后的提示词
  - `provider`
  - `model`

## 润色策略

- 社媒图文场景：强调平台风格、视觉重点、文案语气、画面要素与可生成性。
- 商品图场景：强调主体商品、卖点表达、构图、材质、灯光、场景与详情图信息组织。
- 返回结果必须是单段或多段可直接继续用于生成的提示词文本，不返回解释说明。

## 数据流

1. 用户输入提示词。
2. 前端点击“润色”。
3. 前端调用 `/api/ai/prompt-polish`。
4. 后端复用现有文字模型调用链生成润色文本。
5. 前端回填提示词。
6. 用户继续点击生成，原有生成接口保持不变。

## 错误处理

- 未配置文字模型时，提示无法润色。
- 提示词为空时，前端直接拦截。
- 上游模型返回空内容时，后端返回明确失败信息。
- 润色失败不影响原提示词内容，保持原值不丢失。

## 测试策略

### 前端

- 为提示词润色提取纯函数或可测交互逻辑，覆盖：
  - 空提示词不触发调用
  - 调用成功后回填
  - 调用失败时保留原文本
- 视情况为页面行为补充组件测试或最小单测。

### 后端

- 为 `AiService` 的提示词润色逻辑补测试：
  - 不同场景生成不同系统提示词
  - 上游返回空内容时报错
  - 返回文本时正确透传结构

## 实施步骤

1. 先补后端提示词润色测试与接口测试。
2. 实现后端 DTO、Controller 路由、Service 逻辑。
3. 补前端 API 封装与测试。
4. 重构 `Studio.tsx` 布局并接入润色按钮。
5. 重构 `StudioImages.tsx` 布局并接入润色按钮。
6. 运行前后端测试与必要的构建检查。

## 风险与约束

- 现有页面文本存在编码历史问题，本次不顺手大规模清洗，避免扩大影响面。
- 如果当前页面样式高度耦合单文件实现，布局复刻时需控制改动范围，避免影响草稿箱等相邻页面。
- 润色结果质量依赖当前文字模型配置；本次仅保证流程可用与交互完整，不额外引入质量兜底链路。
