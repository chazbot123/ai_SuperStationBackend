# 审核中心第一版设计

## 背景

当前项目已经存在审核相关入口与页面，包括统一的 `/reviews` 页面、侧边栏中的“审核中心”入口，以及基于前端 store 的素材审核和商品审核能力。但现状仍然偏演示态：

- 审核中心导航还没有拆成明确的业务子模块。
- `Reviews.tsx` 同时承载素材审核与商品审核逻辑，页面职责偏重。
- 素材审核和商品审核虽然都能做基础审批，但交互结构、筛选能力和详情查看仍然不够统一。
- 现阶段需求不是建设完整审核中台，而是先把已有能力收拢成一个统一、轻量、可继续扩展的审核中心。

本次第一版目标是在尽量轻量的前提下，将“素材审核”和“商品审核”统一到一个审核中心页面体系中，并让前端导航结构与页面交互都更清晰。

## 目标

- 将审核中心第一版范围明确收敛为两类审核：
  - 素材审核
  - 商品审核
- 在侧边栏中将“审核中心”拆出两个子模块：
  - 素材审核
  - 商品审核
- 保留统一审核中心入口与统一页面壳，页面主体通过双 Tab 承载两类审核。
- 素材审核按“提交单”粒度审核，一次提交单整单通过或整单驳回。
- 商品审核第一版仅保留“通过 / 驳回”动作，不引入“通过并上架”或复审流。
- 在不重做后端审核领域模型的前提下，尽量复用现有 store 和接口能力完成落地。

## 非目标

- 不在第一版纳入发布审核、关键词审核、规则审核或其他审核类型。
- 不建设审核流配置、审核人分配、复审机制、升级流转等重型中台能力。
- 不新建通用审核后端表结构来统一所有审核对象。
- 不做审核中心总览页、统计大盘或复杂工作台首页。
- 不引入批量审核、批量驳回、批量指派等高级操作。

## 方案对比

### 方案 A：继续在现有 `Reviews.tsx` 上叠加功能

直接在现有页面中继续扩展两个审核区域，增加筛选、详情和导航联动。

优点：
- 改动最少。
- 开发速度最快。

缺点：
- 页面职责会继续膨胀。
- 素材审核与商品审核逻辑耦合更深。
- 后续再增加第三类审核时可维护性较差。

### 方案 B：统一页面壳 + 两个审核子模块

保留统一审核中心入口和整体样式，但将素材审核、商品审核拆成两个模块化面板，共用统一的 Tab、状态展示和交互风格。

优点：
- 符合“统一审核中心但尽量轻量”的目标。
- 结构清晰，便于后续继续增加审核类型。
- 能复用现有数据源，改造成本可控。

缺点：
- 比继续叠加功能多一层拆分工作。

### 方案 C：先抽象完整审核领域模型再做前端

先定义统一审核记录、审核对象类型、审核动作、审核日志服务，再在前后端一起落地。

优点：
- 长期扩展性最好。

缺点：
- 第一版明显过重。
- 与当前“先快速统一已有能力”的目标不匹配。

推荐采用方案 B。

## 页面与路由设计

## 总体结构

- 保留统一审核中心主入口。
- 审核中心页面主体使用双 Tab：
  - 素材审核
  - 商品审核
- 不单独建设总览页。
- 不增加复杂首页统计。

这样既保留统一中心入口，也让两类审核在一个页面体系内切换。

## 路由设计

- 保留 `/reviews` 作为统一审核中心入口。
- 新增两个可直达子路由：
  - `/reviews/materials`
  - `/reviews/products`
- `/reviews` 默认落到素材审核视图。
- 页面内部 Tab 与子路由保持同步：
  - 进入 `/reviews/materials` 时默认选中“素材审核”
  - 进入 `/reviews/products` 时默认选中“商品审核”

这样可以同时满足两个目标：

- 侧边栏子模块可以各自直达对应审核视图。
- 页面内仍然是一个统一审核中心，而不是完全拆成两个独立页面。

## 导航设计

- 侧边栏中的“审核中心”改为可展开父级。
- 子项调整为：
  - 素材审核
  - 商品审核
- 点击子项进入对应子路由。
- 页面主体顶部继续保留 Tab，支持审核员在中心内快速横向切换。

该结构与现有 `studio`、`videos`、`publishing` 等父子导航模式一致，能尽量复用现有侧边栏交互习惯。

## 素材审核设计

## 审核粒度

- 一条素材审核记录代表一次“素材提交单”。
- 一个提交单中可以同时包含：
  - 图片
  - 视频
  - 标题
  - 文案
  - 标签
- 第一版按整单审核：
  - 通过
  - 驳回
- 不做单项分别通过，不拆分图、视频、文案、标题、标签的独立审批。

## 列表展示

素材审核列表每条记录至少展示：

- 提交单标题
- 素材类型
- 提交人
- 提交时间
- 当前状态
- 查看详情入口

其中素材类型需要支持清晰表达以下情况：

- 仅图片
- 仅视频
- 图文
- 视频加文案

第一版列表默认优先展示待审核记录，并支持以下轻量筛选：

- 状态筛选：待审核 / 已通过 / 已驳回
- 关键字搜索：按标题、文案做前端搜索
- 素材类型筛选：图 / 视频 / 混合

## 详情展示

点击“查看详情”后，进入详情抽屉或弹层，展示完整提交内容：

- 图片预览
- 视频预览
- 标题
- 文案
- 标签
- 提交人信息
- 提交时间
- 当前审核状态
- 驳回原因（如有）

第一版详情展示以“快速看全整单信息”为目标，不做多层折叠结构。

## 审核操作

- 操作仅保留“通过”“驳回”两个。
- 驳回时填写驳回原因。
- 驳回原因第一版允许复用统一输入框或弹窗确认，不引入多字段驳回模板。

## 商品审核设计

## 审核粒度

- 一条商品审核记录代表一个商品提审项。
- 第一版仅保留：
  - 通过
  - 驳回
- “通过”只表示审核通过，不在界面语义上强调“通过并上架”。

## 列表展示

商品审核列表每条记录至少展示：

- 商品名称
- 商品摘要
- 价格
- 提交人
- 提交时间
- 当前状态
- 查看详情入口

第一版支持以下轻量筛选：

- 状态筛选：待审核 / 已通过 / 已驳回
- 关键字搜索：按商品名称、摘要做前端搜索

## 详情展示

点击“查看详情”后，在详情抽屉或弹层中展示：

- 商品主图
- 商品名称
- 商品摘要
- 价格
- 更完整描述（如果数据源已有）
- 提交人信息
- 提交时间
- 当前审核状态
- 驳回原因（如有）

## 审核操作

- 审核员可在详情中执行“通过”或“驳回”。
- 驳回时填写驳回原因。
- 第一版不加入“转人工复核”“要求补充资料”等扩展动作。

## 统一交互设计

- 审核中心主体顶部为双 Tab。
- 每个 Tab 各自维护自己的筛选、列表和详情区域。
- 列表行内保留“查看详情”动作。
- 审核动作建议放在详情抽屉或弹窗底部，避免在表格行内直接堆过多按钮。
- 驳回操作统一弹出原因输入，减少页面内散落输入框。

为保证实现轻量且风格统一，第一版优先复用现有项目中的 `Drawer`、`Modal`、`Tabs`、`Badge`、`Table` 组件。

## 组件拆分设计

建议前端拆分为以下结构：

- `Reviews.tsx`
  - 作为审核中心页面壳
  - 负责子路由或 Tab 同步
  - 负责顶部 Tab 切换
  - 负责挂载具体审核面板
- `MaterialReviewsPanel.tsx`
  - 负责素材审核列表、筛选、详情和审核动作
- `ProductReviewsPanel.tsx`
  - 负责商品审核列表、筛选、详情和审核动作
- `ReviewStatusBadge.tsx`
  - 统一渲染待审核、已通过、已驳回等状态表现
- `ReviewRejectDialog.tsx` 或复用现有 `Modal`
  - 统一承载驳回原因输入

这样可以避免 `Reviews.tsx` 继续增长为“大而全页面”，同时保持第一版拆分粒度适中。

## 数据设计与接法

## 商品审核数据源

商品审核继续复用现有前端数据接法：

- store：`src/store/productsStore.ts`
- 审核通过：`approveProduct(id)`
- 审核驳回：`rejectProduct(id, reason)`

第一版不额外新增统一审核 API 层。

## 素材审核数据源

素材审核第一版继续复用：

- store：`src/store/appStore.ts`
- 数据集合：`contents`
- 审核更新：`updateContent(contentId, patch)`

为了避免页面直接耦合底层 `ContentItem` 结构，前端应增加一层轻量“素材审核视图模型”映射，用于整理列表与详情所需字段，例如：

- 审核记录 ID
- 标题
- 素材类型标签
- 图片集
- 视频地址
- 文案
- 标签
- 提交人信息
- 提交时间
- 审核状态
- 驳回原因

## 状态映射

第一版统一审核状态口径：

- 待审核
- 已通过
- 已驳回

素材审核可直接映射现有 `reviewStatus`：

- `submitted` -> 待审核
- `approved` -> 已通过
- `rejected` -> 已驳回

商品审核可映射现有 `status`：

- `submitted` -> 待审核
- `live` 或审核通过态 -> 已通过
- `rejected` -> 已驳回

为减少第一版范围，商品审核页面不在审核中心内单独展示 `draft`、`offline` 等非审核态记录。

## 数据流

1. 用户通过侧边栏子项或 `/reviews` 进入审核中心。
2. 页面根据当前子路由确定默认 Tab。
3. 审核中心页面壳加载素材审核面板或商品审核面板。
4. 各面板从现有 store 中读取数据并做前端筛选映射。
5. 审核员点击“查看详情”进入详情抽屉或弹窗。
6. 审核员执行“通过”或“驳回”。
7. 前端调用现有 store 方法更新状态。
8. 列表与详情状态同步刷新。

## 错误处理

- 商品审核沿用现有 `productsStore` 的错误返回方式，在面板内显示轻量错误提示。
- 素材审核因为第一版主要是本地 store 更新，错误处理以输入校验和状态更新保护为主。
- 驳回时如果需要驳回原因，则前端在提交前做非空校验。
- 若详情目标记录因状态变化消失，应自动关闭详情面板或提示记录已更新。

## 测试策略

## 前端

- 为审核中心页面新增基础交互测试，覆盖：
  - 默认 Tab 选择
  - Tab 与子路由同步
  - 素材审核列表筛选
  - 商品审核列表筛选
  - 查看详情交互
  - 驳回原因输入与提交流程
- 为素材审核视图模型映射提取可测试的纯函数时，优先补最小单测。

## 回归关注点

- 侧边栏父子导航展开行为不能影响现有 `studio`、`videos`、`publishing`、`rbac` 的交互。
- `/reviews`、`/reviews/materials`、`/reviews/products` 的默认跳转与高亮状态需一致。
- 现有商品审核接口行为不能因页面重构而被改变。

## 风险与约束

- 当前代码库中已存在一定数量的页面与 store 在并行开发中变动，审核中心改造需要尽量限制写入范围，避免误伤其他页面。
- 素材审核当前主要基于前端 demo store，第一版只能保证统一页面体验，不能等同于完整服务端审核系统。
- 现有 `Sidebar.tsx` 和 `Reviews.tsx` 已承担较多职责，改造时需要控制拆分节奏，避免在第一版引入过度抽象。

## 验收标准

- 侧边栏“审核中心”存在两个清晰子模块：素材审核、商品审核。
- `/reviews` 作为统一审核中心页面可正常展示双 Tab。
- 通过导航进入子模块时，页面能定位到正确 Tab。
- 素材审核支持按提交单查看并整单通过或驳回。
- 素材审核详情能展示图/视频、标题、文案、标签和提交信息。
- 商品审核支持查看详情并执行通过或驳回。
- 商品审核页面语义中不再强调“通过并上架”。
- 第一版不引入总览页、批量审核、复审流或审核规则配置。
