# 任务计划

## 目标
- 将 `ZL_Supersite` 从单 HTML demo 升级为可维护、可启动的独立前端项目。
- 保留现有首页视觉内容与素材目录，为后续超级站公开接口接入预留结构。
- 第一阶段先完成项目骨架、首页迁移与本地启动验证，不扩接口联调。

## 决策记录
- 当前页面为单 HTML 内联样式和脚本的静态落地页。
- 需要兼顾“先整理结构”与“后续可接 API”的演进空间。
- 当前主仓库前端已使用 `React + Vite`，`ZL_Supersite` 首版独立项目沿用同栈，减少后续复用成本。
- 第一阶段不追求一次性拆完所有动效脚本，先保首页主链路可运行。
- 用户当前优先级变更为“先恢复旧稿全部交互元素、页面样式和图片”，因此本轮优先选择低风险恢复方案，而不是继续组件细拆。
- 当前恢复方案优先保留旧稿原始 HTML/CSS/JS，在新项目入口中原样承载，后续再逐步替换为组件化实现。
- 旧稿当前通过 `public/legacy-home.html + iframe` 方式挂回新项目首页，优先保证视觉与交互一致性。
- 顶部运营指标模块当前先在旧稿页内接入真实公开接口，避免整页尚未拆回 React 前阻塞前台落地。
- AI 客服模块继续沿用旧稿聊天面板壳子，但消息与会话状态改为直接调用 `support/public` 接口，不再用本地 `setTimeout` 假回复。
- 本轮不重写旧稿交互逻辑，优先抽离为 `React DOM 容器 + 原样样式/脚本`，只替换承载方式。
- 粒子与滚动动效继续沿用 `p5 + gsap + ScrollTrigger + Lenis`，避免改动画实现造成回归。

## 风险
- 直接大拆可能导致资源路径失效。
- 根目录存在历史脚本和测试文件，需区分“运行必要”与“应归档/删除”。
- 原需求文档当前未在项目目录中找到，本轮继续以代码整理为主。
- 原首页脚本体量大且强依赖全局 DOM，迁移到组件化结构时需控制改动范围，避免首轮就引入大量交互回归。
- 若直接整块搬运全部内联脚本，后续接 API 会继续难维护；需在“先跑起来”和“可持续演进”之间做最小平衡。
- 旧稿当前至少有一张产品图 `assets/images/products/prod2.png` 缺失；恢复时需要补位或改指向，否则会出现单卡片空图。
- `iframe` 恢复方案适合当前“先还原”，但后续接公开接口前仍建议逐步将旧稿拆回 React 组件，避免长期双层页面结构。
- 前台指标读取当前依赖 `?userId=` 识别站点归属；正式上线前仍建议补 `slug/domain` 方案，避免公开站点直接暴露用户 ID。
- 客服前台当前仍在 `legacy-home.html` 内承接，后续如果继续扩展留资表单、转人工状态 UI，建议再拆回独立 React 组件。
- 旧稿脚本包含 `p5` 全局 `setup/draw` 与大量全局 DOM 查询，若重复初始化会冲突；迁移时需保证脚本只初始化一次。
